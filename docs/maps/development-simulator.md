# Симулятор поездки для разработки

`apps/api/scripts/simulate-trip.ts` — проходит полный жизненный цикл одной
поездки через настоящие HTTP-эндпоинты бэкенда, без реального телефона:
пассажир, водитель, машина, поиск, отклик, выбор, оплата, подача,
поездка, завершение — плюс проигрывание GPS-координат вдоль настоящей
геометрии маршрута с эмуляцией сетевых и локационных сбоев.

## Запуск

```
pnpm dev:simulate-trip
```

(из корня репозитория; эквивалент `pnpm --filter @resilient-taxi/api simulate:trip`,
т.е. `tsx scripts/simulate-trip.ts` внутри `apps/api`). Требует поднятого
API и его Postgres/Redis (`pnpm infra:up` + `pnpm --filter @resilient-taxi/api dev`,
либо аналогичный локальный запуск) и переменных окружения из корневого
`.env` (`DATABASE_URL`, `AUTH_JWT_SECRET`, при нестандартном порте/хосте —
`API_URL`).

Каждый запуск идемпотентен относительно предыдущего: тестовые
пассажир/водитель — фиксированные номера (`+79995550001`/`+79995550002`),
профиль и машина водителя — upsert, а перед выходом на линию скрипт вызывает
настоящий `POST /drivers/me/offline`, который сбрасывает кэш последней
позиции водителя в Redis — без этого шага позиция, оставшаяся от
предыдущего запуска, может показаться физически недостижимой для первой же
точки нового запуска и будет отклонена проверкой правдоподобности скорости.

## Сознательные упрощения (не баги)

- **Обход OTP**: `mintAccessToken` вручную подписывает access-токен тем же
  алгоритмом/секретом (`AUTH_JWT_SECRET`, HS256), что и
  `AuthService.createAccessToken`, и создаёт соответствующую
  `DeviceSession` — токен проходит настоящий `AccessTokenGuard`, но без
  реального SMS/OTP-цикла.
- **Прямая запись подбора водителя** (`seedDispatchMatch`): реальный
  dispatch-движок работает асинхронно и ищет кандидатов сам; здесь
  результат (`DispatchAttempt`/`DispatchAttemptLog`) вставляется напрямую
  в БД — воспроизводить асинхронный поиск кандидатов здесь означало бы
  тестировать сам поиск, а не жизненный цикл поездки.

Все остальные шаги (создание поездки, отклик, выбор, оплата, статусы,
геолокация, `/routes/build`) идут через настоящие HTTP-эндпоинты.

## Проигрывание GPS вдоль маршрута (`driveAlong`)

Каждый отрезок пути (до точки подачи, от подачи до назначения) строится
через настоящий `POST /routes/build` и передискретизируется
(`resample`) на шаг `DRIVE_SPEED_METERS_PER_SECOND * STEP_SECONDS`.

### Почему проигрывание не в реальном времени

Реалистичная скорость (~40 км/ч) для маршрута в 17 км потребовала бы
десятки реальных минут только на один участок — непригодно для скрипта,
запускаемого вручную при разработке. Вместо этого используется
**симулированные часы**, продвигающиеся на `STEP_SECONDS` (5 с) за каждую
точку, независимо от того, сколько реального времени занял сам HTTP-запрос:
подразумеваемая скорость между двумя принятыми точками равна ровно
`DRIVE_SPEED_METERS_PER_SECOND` (80% от
`DRIVER_LOCATIONS_MAX_PLAUSIBLE_SPEED_METERS_PER_SECOND`, по умолчанию
56 м/с) — по построению, а не за счёт реальной задержки между запросами.

Так как симулированные часы убегают вперёд от настоящего времени,
`driveAlong` следит за разрывом (`simulatedNow - Date.now()`) и, если он
превышает бюджет (`DRIVER_LOCATIONS_FUTURE_TOLERANCE_SECONDS − 30 с` —
запас под порог сервера «дата не может быть в будущем»), **приостанавливает
скрипт в реальном времени**, пока разрыв снова не окажется в пределах
бюджета. Для маршрутов, укладывающихся в бюджет целиком (как оба тестовых
плеча — Московский вокзал → Невский, Невский → Пулково), пауза обычно не
требуется вовсе, и весь прогон занимает секунды, а не минуты; для более
длинных маршрутов скрипт корректно, хоть и медленнее, доедет до конца.

### Сценарии внутри одного участка

На каждом участке (~30%, ~50%, ~70% точек) проигрывается один из четырёх
особых случаев — **дополнительным** запросом рядом с обычной точкой пути,
а не вместо неё, чтобы отклонённый/устаревший/потерянный сценарный запрос
никогда не сбивал темп и подразумеваемую скорость последующих настоящих
точек маршрута:

- `network_loss` — запрос к заведомо недостижимому адресу
  (`http://127.0.0.1:1`, таймаут 300 мс) — настоящий сетевой сбой, а не
  просто пропущенный вызов, так что путь восстановления (перехват,
  логирование, продолжение) действительно проверяется.
- `stale` — та же точка, но с `recordedAt` на 120 с в прошлом (старше
  `DRIVER_LOCATIONS_STALE_AFTER_SECONDS`) — сервер принимает её
  (`accepted`), но помечает как `stale` и не обновляет «текущую» позицию.
- `gps_jump` — та же точка со сдвигом +0.45° по широте/долготе (~50 км) —
  сервер корректно отклоняет её как физически невозможную
  (`IMPOSSIBLE_LOCATION_SPEED`).
- `recovery` — следующая после `gps_jump` точка отправляется как обычно
  (её отклонённый предшественник не сдвинул «текущую» позицию сервера) —
  демонстрирует восстановление после скачка без какой-либо специальной
  обработки.

## Известное поведение при частых повторных запусках подряд

Каждый запуск отправляет ~80–90 обновлений локации в течение нескольких
секунд реального времени. При повторном запуске сразу же после
предыдущего оба набора запросов попадают в одно и то же скользящее
60-секундное окно ограничителя скорости
(`DRIVER_LOCATIONS_RATE_LIMIT_PER_MINUTE`, 120/мин) и часть точек в
хвосте второго прогона может быть отклонена с `429
LOCATION_RATE_LIMITED`. Это верно работающий ограничитель, а не дефект
симулятора: жизненный цикл поездки при этом всё равно доходит до
`trip.completed`/`SETTLED`, поскольку завершение поездки не требует, чтобы
каждое обновление локации было принято. Одиночный запуск (без повторов
впритык) отклонений не создаёт вовсе, кроме двух намеренных `gps_jump`.

## Ограничения

- Не подключает реальный телефон/эмулятор — только HTTP.
- Не покрывает push-уведомления, экран пассажира/водителя как таковой —
  только серверную часть конвейера, которую эти экраны используют
  (см. `passenger-map-flow.md`/`driver-map-flow.md` про то, что фактически
  подключено на стороне UI).
