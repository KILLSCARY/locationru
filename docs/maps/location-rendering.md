# Отрисовка живой позиции: сглаживание, качество, синхронизация

Общий контракт продублирован параллельно на TypeScript
(`apps/passenger-mobile/src/maps/`) и Kotlin
(`apps/driver-android/core/maps/`) с одинаковой семантикой — правки в одном
языке должны сопровождаться зеркальной правкой в другом.

## `LocationQualityStatus`

Тип (`locationQuality.ts` / `LocationQualityStatus.kt`):
`STABLE | DEGRADED | STALE | SPOOFING_SUSPECTED | UNAVAILABLE`.

`classifyLocationQuality(sample, previous, nowMs, thresholds)` определяет
статус в таком порядке приоритета (первое совпадение побеждает):

1. `UNAVAILABLE` — возраст засечки больше
   `unavailableAfterSeconds` (по умолчанию 60 с,
   `MAP_LOCATION_UNAVAILABLE_SECONDS`).
2. `STALE` — возраст больше `staleAfterSeconds` (по умолчанию 15 с,
   `MAP_LOCATION_STALE_SECONDS`), но не превысил `UNAVAILABLE`.
3. `SPOOFING_SUSPECTED` — подразумеваемая скорость между этой и предыдущей
   засечкой выше `maxPlausibleSpeedMetersPerSecond` (55 м/с ≈ 200 км/ч).
4. `DEGRADED` — заявленная точность (`accuracyMeters`) хуже
   `degradedAccuracyMeters` (50 м).
5. `STABLE` — иначе.

Свежесть проверяется раньше правдоподобности скорости намеренно: старая
точка не должна рассматриваться как «подмена», даже если формально из неё
следует большая скорость.

### Правила отрисовки по статусу

| Статус               | passenger-mobile (пассажир)                                                                                                                                                                                         | driver-android (водитель)                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `STABLE`             | маркер плавно едет к новой точке, сообщение не показывается                                                                                                                                                         | обычная отрисовка                                                                          |
| `DEGRADED`           | маркер обновляется как обычно, нейтральное сообщение «Уточняем положение машины…»                                                                                                                                   | «Слабый сигнал геолокации — точность снижена»                                              |
| `STALE`              | выборка **не** передаётся в интерполятор — маркер замирает на последней доверенной точке; сообщение «Обновляем положение машины…» (время последнего обновления доступно через `renderedDriver`/`previousRawSample`) | «Нет свежих данных геолокации»                                                             |
| `SPOOFING_SUSPECTED` | выборка **не** передаётся в интерполятор — сохраняется последняя доверенная точка; нейтральное сообщение пассажиру («Временная неточность...») — без слова «подмена»                                                | явное предупреждение водителю: «Похоже на подмену геолокации — координаты не используются» |
| `UNAVAILABLE`        | как `STALE` по эффекту на маркер (координат просто нет)                                                                                                                                                             | «Геолокация недоступна»                                                                    |

`passengerMessageFor`/`driverMessageFor` — единственные функции,
формирующие текст; экран лишь показывает то, что они вернули.

## `DriverMarkerInterpolator`

Сглаживает GPS-обновления так, чтобы маркер не телепортировался на каждое
WS-событие:

- `ingest(sample, receivedAtMs)` → `'accepted' | 'stale_ignored' | 'implausible_speed_ignored'`.
  - `stale_ignored` — `recordedAt` новой засечки не позже текущей целевой
    (`to`) — защита от обновления назад без причины.
  - `implausible_speed_ignored` — скорость между текущей целевой и новой
    засечкой выше `maxPlausibleSpeedMetersPerSecond` — единственный явный
    признак `SPOOFING_SUSPECTED`, дополняющий возрастной критерий в
    `classifyLocationQuality`.
- `positionAt(nowMs)` — линейная интерполяция (`lerpPoint`/`lerpBearing`)
  между «откуда» (`from`, текущее отрендеренное положение на момент нового
  `ingest`) и «куда» (`to`, последняя принятая засечка) за
  `animDurationMs = min(gap между recordedAt, maxDurationMs)`, либо
  `defaultDurationMs` (`MAP_DRIVER_INTERPOLATION_MS`, 1000 мс по
  умолчанию), если разрыв между засечками неположительный (переслано не по
  порядку, но всё ещё новее текущей цели).
- Пропуск засечек (сеть моргнула, несколько WS-сообщений сразу) — не
  ломает интерполяцию: следующая принятая засечка просто становится новой
  целью, а анимация стартует от текущего отрендеренного положения, а не
  от последней «официальной» точки, — визуально нет рывка назад.
- Ограничение неправдоподобной скорости не даёт скачку (например,
  дублированный/испорченный пакет с координатами за 50 км) сдвинуть
  маркер — такая засечка просто отбрасывается, а разрешение вопроса
  «доверять ли ей вообще» отдаётся `classifyLocationQuality`/UI выше.
- Юнит-тесты: `DriverMarkerInterpolator.test.ts` /
  `DriverMarkerInterpolatorTest.kt` — фиксируют физически правдоподобный
  шаг (~11 м/с ≈ 40 км/ч на 1 с), не 0.01° за секунду (~1100 м/с), что
  сперва ошибочно попало в тестовые данные и отбраковывалось интерполятором
  как раз корректно.

## Камера

См. `passenger-map-flow.md`/`mobile-map-architecture.md` —
`MapCameraController`/`MapController` защищены от «дёрганья» камеры
порогами `minMoveMetersToRecenter` (8 м) и `minBearingChangeDegrees` (12°),
и отключают автослежение при ручном перетаскивании (кнопка «Вернуться к
машине» его восстанавливает).

## Синхронизация WebSocket-событий

`RoomSequenceTracker` (`eventSequence.ts` / `RoomSequenceTracker.kt`)
отслеживает номер последовательности каждого события в комнате поездки:

- `observe(sequence)` → `'apply'` (следующий по порядку),
  `'duplicate_or_old'` (номер не больше текущего — игнорируется),
  `'gap_detected'` (пропуск — есть номера между текущим и полученным).
- При `gap_detected` клиент запрашивает довосстановление через
  существующий WS-механизм бэкенда `events.replay`
  (`RealtimeOutboxService`, комнаты `userRoom`/`tripRoom`,
  таблица `realtime_room_sequences`). **У бэкенда нет отдельного
  REST-эндпоинта ресинка** — задание описывает его как «REST resync»,
  здесь это осознанно реализовано через уже существующий WS-канал вместо
  добавления параллельного REST-пути для того же самого.
- Один сокет на сессию (`src/api/realtime.ts` — модульный синглтон
  `getSocket()`), никогда не открывается второе соединение параллельно.
- Переподключение — с экспоненциальным backoff (настройки `reconnection`
  в опциях socket.io); токен передаётся через функцию
  `auth: (callback) => callback({ token })`, так что обновление токена
  подхватывается при следующей попытке подключения без пересоздания
  сокета.
- Подписка на комнату поездки снимается (`unsubscribe`) при размонтировании
  экрана — не оставляет фоновых слушателей.
