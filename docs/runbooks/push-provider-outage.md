# Runbook: отказ FCM/APNs (провайдера push-уведомлений)

## Быстрая диагностика

1. **Метрики** (`GET /metrics`): резкий рост `push_failed_total` /
   `push_dead_letter_total`, падение `push_provider_accepted_total`
   относительно `push_send_attempts_total`, рост `push_provider_latency_ms`
   и `notification_outbox_lag_seconds` — см. `../notifications/monitoring.md`
   за точными PromQL-примерами.
2. **Снимок для человека**: `GET /admin/notifications/push-stats` —
   посмотреть `outboxByStatus` (много `PROCESSING`/`PENDING` — воркер не
   успевает или откатывается по ретраям) и `notificationsByStatus`.
3. **Конкретные события**: `GET /admin/notifications/dead-letter` — читать
   `lastError` (обрезан до 512 символов, но обычно достаточно, чтобы
   отличить сетевой таймаут от `messaging/invalid-argument` от реального
   отказа Firebase).
4. **Логи API**: искать `event: 'push.firebase_request_failed'` (только
   классифицированный код ошибки — сырой текст с токеном никогда не
   логируется, см. `../notifications/privacy.md`) и
   `event: 'push.outbox_dispatch_failed'` (сбой самого цикла опроса
   воркера, а не отдельной отправки).

## Circuit breaker (`FirebasePushProvider`)

`FirebasePushProvider` оборачивает каждый вызов Firebase Admin SDK в
`CircuitBreaker` (`apps/api/src/maps/providers/circuit-breaker.ts`,
переиспользован из maps-модуля) с параметрами
`{ failureThreshold: 5, openMs: 30_000 }`:

- 5 подряд неудачных (retryable) вызовов подряд → цепь переходит в `open`
  на 30 секунд — все последующие вызовы в этом окне **не доходят до
  Firebase вообще**, сразу возвращается `PushProviderError.circuitOpen`
  (в `NotificationOutboxWorker` это превращается в обычный retryable-исход
  — событие уходит на стандартный backoff, см. `../notifications/retries.md`).
- По истечении `openMs` — одна пробная попытка (`half_open`): успех
  закрывает цепь и сбрасывает счётчик отказов, неудача — снова открывает
  цепь ещё на 30 секунд.
- Это защита самого API-процесса от траты времени/потоков на заведомо
  недоступный Firebase, а не замена ретраев outbox — оба механизма работают
  вместе: пока цепь открыта, outbox продолжает копить события и ретраить их
  по расписанию `retries.md`, просто без реальных сетевых вызовов в это
  окно.

## Что происходит с пользователями во время отказа

**Push — никогда не единственный источник истины.** Оба клиента
(driver-android, passenger-mobile) при открытии приложения или по
WebSocket-событию сами перезапрашивают актуальное состояние (список
заказов, статус активной поездки, инбокс уведомлений) — отказ push не
блокирует работу приложения, только задерживает уведомление пользователя о
новом событии, если приложение не открыто. Реализация уже устроена так,
что:

- outbox продолжает копить события (не теряет их — Postgres, не in-memory
  очередь);
- при восстановлении Firebase накопленные `PENDING`/ретраящиеся события
  начнут доставляться сами, как только `canRequest()` снова начнёт
  пропускать вызовы;
- события, у которых истёк TTL до момента восстановления (см. `NEW_ORDER`
  TTL = 30с — самый нетерпимый к задержке тип), помечаются `EXPIRED` и
  push на них уже не уйдёт — но данные, стоящие за событием (например,
  сам заказ), никуда не пропадают: они видны через обычный REST/WebSocket
  запрос, push тут был просто способом привлечь внимание быстрее.

## Восстановление

1. Дождаться закрытия цепи (`openMs` = 30с после последнего отказа) —
   ничего вручную делать не нужно, `CircuitBreaker` переходит в `half_open`
   сам.
2. Проверить `push_provider_accepted_total`/`push_send_attempts_total` —
   отношение должно вернуться к обычному уровню (близко к 1 в норме).
3. Если много событий успело уйти в `DEAD_LETTER` за время отказа (типичная
   причина — `maxAttempts=5` исчерпался при большом времени простоя) —
   разобрать `GET /admin/notifications/dead-letter`, отфильтровать по
   `lastError`, соответствующему именно этому инциденту (например,
   `'firebase circuit is open'`/сетевой таймаут), и одним проходом вызвать
   `POST /admin/notifications/dead-letter/:eventId/retry` на каждое —
   ручного bulk-эндпоинта нет, только по одному событию (см. известные
   пробелы ниже).

## Если недоступен весь Firebase-проект (не временный сбой, а, например,

## удалённые/просроченные credentials)

1. Проверить, что `FIREBASE_PROJECT_ID`/`FIREBASE_CLIENT_EMAIL`/
   `FIREBASE_PRIVATE_KEY` актуальны (см. `../notifications/fcm.md`) —
   часто причина именно в истёкшем/отозванном сервисном аккаунте, а не в
   отказе самого Firebase.
2. Как временная мера — переключить `PUSH_PROVIDER=development` (события
   продолжат создавать `Notification`/инбокс-записи, но реальные push не
   уйдут никому) **только если** это осознанный компромисс на время
   восстановления; в норме лучше держать `fcm` и дать outbox ретраить, чем
   тихо отключать push для всех пользователей.

## Известные пробелы (честно, не «доделать позже» тихо)

- Нет bulk-ретрая dead-letter событий — только по одному `eventId`. При
  массовом инциденте (например, Firebase был недоступен полчаса) это
  требует ручного прохода по списку через `GET .../dead-letter`
  (постранично) и по одному ретраю на каждое.
- Circuit breaker — per-process, in-memory, не разделяется между
  несколькими инстансами API (при горизонтальном масштабировании каждый
  под считает отказы независимо) — при частичном отказе (например, DNS
  проблема только у части подов) поведение будет неравномерным между
  инстансами. Для текущего масштаба (staging/один процесс) это не
  проблема, но при горизонтальном масштабировании API стоит рассмотреть
  вынос состояния цепи в Redis.
- Нет отдельного алерта именно на "цепь открыта" (`CircuitState`
  не экспортируется как метрика) — обнаруживается косвенно через
  `push_failed_total`/`push_provider_latency_ms`, не напрямую.
- Нет автоматического уведомления on-call при массовом dead-letter —
  только PromQL-примеры в `../notifications/monitoring.md`; реальный
  Prometheus/Alertmanager в этой инфраструктуре пока не развёрнут (тот же
  дисклеймер, что и в `otp-incident-response.md`).
