# Настройка SMS.RU: что нужно сделать владельцу проекта

Это единственный документ, который описывает **ручные шаги в личном
кабинете SMS.RU** — код ничего из этого сделать не может.

## 1. Получить API-ID

1. Зарегистрироваться на https://sms.ru (или войти в существующий
   аккаунт).
2. Личный кабинет → «Настройки» → «API» — скопировать **API ID**
   (не логин/пароль — именно `api_id`, используется во всех запросах).
3. Положить значение в `SMS_RU_API_ID` в `.env` соответствующего
   окружения (staging/production) — **никогда не коммитить** реальное
   значение в git (в `.env.example`/`.env.staging.example` там только
   плейсхолдеры).

## 2. Пополнить баланс

Отправка SMS платная. Пополнить баланс в личном кабинете на сумму,
достаточную для ожидаемого объёма OTP-кодов (см. `pnpm
staging:test:sms` — тестовая отправка тоже списывает деньги).
Мониторинг остатка — `GET /api/v1/admin/auth/sms-balance`
(роль ADMIN/SUPER_ADMIN) в админке.

## 3. Зарегистрировать имя отправителя (Sender ID) — опционально

Если нужно, чтобы SMS приходили от имени «ResilientTaxi» (а не с
короткого номера SMS.RU по умолчанию):

1. Личный кабинет → «Имена отправителей» → подать заявку на новое имя
   (например, `ResilientTaxi`), пройти модерацию SMS.RU (может занять
   от нескольких часов до нескольких дней).
2. После одобрения — указать это имя в `SMS_SENDER_ID`.
3. Если `SMS_SENDER_ID` пусто — `SmsRuProvider` отправляет без
   параметра `from`, сообщения идут с дефолтного отправителя SMS.RU.
   Это безопасный fallback, ничего не ломается.

## 4. Настроить callback (webhook) статуса доставки

1. Личный кабинет → «Настройки» → «Уведомления о статусе доставки» (или
   аналогичный раздел — точное название пункта меню может отличаться в
   актуальном интерфейсе SMS.RU, сверьтесь с их текущей документацией).
2. Указать URL вида:

   ```
   https://<ваш-домен>/api/v1/webhooks/sms/sms-ru?token=<SMS_RU_WEBHOOK_SECRET>
   ```

   `<SMS_RU_WEBHOOK_SECRET>` — тот же секрет, что в `.env` (сгенерировать
   через `openssl rand -base64 32`, не короче 16 символов). Это
   единственный механизм аутентификации вебхука — SMS.RU не подписывает
   свои callback'и, поэтому секрет передаётся прямо в URL.

3. **Важно:** сначала сгенерировать и задеплоить `SMS_RU_WEBHOOK_SECRET`
   в окружение, потом регистрировать URL с этим секретом в кабинете —
   иначе первые callback'и получат 401 и будут потеряны (SMS.RU не
   ретраит их бесконечно).
4. (Опционально, вторичная защита) Если SMS.RU публикует список своих
   исходящих IP для callback'ов — прописать его в
   `SMS_RU_WEBHOOK_IP_ALLOWLIST` (через запятую). Это **не основная**
   проверка подлинности (см. `docs/auth/sms-ru-webhook.md`), а
   дополнительный слой — если список пуст, эта проверка просто не
   применяется.

## 5. Проверить интеграцию перед продакшном

```bash
STAGING_SMS_TEST_PHONE=+7<ваш номер> pnpm staging:test:sms
```

Скрипт (`apps/api/scripts/staging-test-sms.ts`):

- отказывается запускаться где угодно, кроме `APP_ENV=staging`;
- проверяет `healthCheck()` (доступность `/my/balance`);
- печатает текущий баланс;
- отправляет одно **реальное** транзакционное SMS (не проходит через
  `OtpService`, это не OTP-код) на указанный номер;
- опрашивает статус доставки до 5 раз с паузой 2 секунды;
- завершается ненулевым кодом при любой ошибке.

Сверьте фактические `status_code` в выводе скрипта и в личном кабинете
SMS.RU с таблицей в `sms-ru.status.ts` (см.
`docs/auth/sms-providers.md#нормализация-статусов`) — если коды не
совпадают, поправьте маппинг до продакшн-запуска.

## 6. Переключить окружение на `sms-ru`

После успешной проверки:

```
SMS_PROVIDER=sms-ru
SMS_RU_API_ID=<реальный api_id>
SMS_RU_WEBHOOK_SECRET=<реальный секрет>
```

В production `env.validation.ts` требует именно `sms-ru` (либо явный
провал старта приложения) — `development`/`staging` там недопустимы.

## Что НЕ входит в эту интеграцию

- Реальные звонки (flash call / звонок с кодом) — не реализованы,
  `GET /api/v1/auth/channels` честно возвращает их как `available:
false`.
- Автоматическое переключение на резервный канал без согласия
  пользователя — не реализовано (архитектурно предусмотрено, см.
  `VerificationChannel`, но нет второго провайдера, на который
  переключаться).
