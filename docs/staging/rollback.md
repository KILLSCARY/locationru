# Откат staging-деплоя

Это самый важный документ, чтобы прочитать честно: здесь нет одной
кнопки «откатить всё». Есть три независимых уровня, у каждого — свой
механизм и свои ограничения.

## 1. Откат кода/образов приложения

`docker-compose.staging.yml` объявляет `image:` с тегом, который CI
выставляет равным commit SHA. Откатить код — значит задеплоить
СЛЕДУЮЩИЙ (предыдущий по времени) уже собранный SHA-тег:

```bash
export STAGING_API_IMAGE=ghcr.io/<repo>-api:<предыдущий-sha>
export STAGING_ADMIN_IMAGE=ghcr.io/<repo>-admin-web:<предыдущий-sha>
docker compose -f docker-compose.staging.yml --env-file .env.staging pull api admin-web
docker compose -f docker-compose.staging.yml --env-file .env.staging up -d --wait
```

Это безопасно и обратимо — оба образа для каждого коммита остаются в
GHCR (никуда не удаляются автоматически).

## 2. Откат данных (Postgres)

`pnpm staging:restore --yes [файл]` — восстанавливает дамп,
сделанный `pg_dump`. Подробности и гарантии — `docs/staging/backups.md`.
Это возвращает данные к состоянию НА МОМЕНТ БЭКАПА — любые записи,
созданные после этого момента, теряются безвозвратно (restore.sh
дополнительно бэкапит текущее состояние перед восстановлением именно
поэтому — если восстановление было ошибкой, у вас остаётся бэкап
состояния прямо перед ним).

## 3. Откат схемы (Prisma-миграции) — честное предупреждение

**Prisma не откатывает миграции автоматически.** `prisma migrate deploy`
умеет только применять миграции вперёд — команды «отменить последнюю
миграцию» в Prisma CLI не существует. Если задеплоенная миграция должна
быть отменена, есть только два реальных варианта:

- **Восстановить БД из бэкапа**, сделанного до применения этой миграции
  (см. раздел 2 выше) — это откатывает и данные, и схему одновременно,
  теряя всё, что произошло после бэкапа.
- **Написать и применить новую миграцию**, которая вручную отменяет
  изменения предыдущей (например, `DROP COLUMN`, если предыдущая
  миграция делала `ADD COLUMN) — это ВПЕРЁД по времени операция, просто
с противоположным эффектом, а не настоящий откат состояния `_prisma_
  migrations`.

Никакого третьего пути (ни `prisma migrate rollback`, ни аналога) в этой
версии Prisma нет. Планируйте деплой миграций соответственно: если
миграция потенциально деструктивна (удаление колонки/таблицы), делайте
дополнительный ручной бэкап непосредственно перед её накатом, независимо
от расписания автоматического бэкапа.

## Когда деплой считается неудачным

`pnpm staging:deploy` печатает инструкции по откату (пункт 2 выше) и
завершается с ненулевым кодом в любом из случаев:

- `docker compose up --wait` не дождался healthy-состояния;
- `/health/ready` не ответил `ok` за отведённое время;
- smoke-тест провалился — **даже если контейнеры уже запущены**:
  «запущено» и «проверено и работает» — разные вещи, и скрипт никогда не
  путает одно с другим.
