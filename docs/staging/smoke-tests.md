# Smoke-тест staging

`pnpm staging:smoke` (`scripts/staging/smoke.sh` →
`apps/api/scripts/staging-smoke.ts`, запускается внутри контейнера,
собранного из образа `migrate`, чтобы иметь прямой доступ к Postgres/
Redis/MinIO и к `api`/`admin-web` по внутренним DNS-именам, ещё до того,
как DNS/TLS публичного домена обязательно готовы).

## Что проверяется

1. **Health**: `/health`, `/health/live`, `/health/ready` — все должны
   вернуть `status: "ok"`.
2. **Аутентификация SUPER_ADMIN** (см. раздел про bootstrap ниже) и
   тестовых пассажира/водителя (через реальный
   `GET /api/v1/admin/staging/otp/:phone`).
3. **Полный жизненный цикл поездки** по-настоящему через HTTP: создание
   → старт поиска → ставка водителя → выбор → подтверждение выезда →
   авторизация платежа → выезд → прибытие → посадочный код → старт →
   завершение → финальный статус `SETTLED`.
4. **Доставка realtime-события через WebSocket**: клиент подключается,
   входит в комнату поездки, и тест ждёт реального прихода события
   `trip.searching` по сокету (не просто проверяет HTTP-ответ).
5. **Object storage**: получение presigned upload URL, реальный `PUT` в
   MinIO, подтверждение загрузки, presigned download URL, побайтовое
   сравнение содержимого.
6. **Аудит-лог**: подтверждение, что просмотры OTP реально записались в
   `admin_audit_logs`.
7. **Очистка**: вызывает `reset-test-data`, чтобы не копить тестовые
   поездки между запусками.

Скрипт завершается ненулевым кодом при любой неудаче — это то, на чём
`pnpm staging:deploy` и CI gate'ят успешность деплоя.

## Bootstrap SUPER_ADMIN: почему это не «просто ещё один логин»

Первый вход SUPER_ADMIN — настоящая курица-и-яйцо проблема: эндпоинт
просмотра OTP (`GET /api/v1/admin/staging/otp/:phone`) сам требует
токен SUPER_ADMIN, а другого SUPER_ADMIN, который мог бы посмотреть его
код, ещё не существует. Решение: этот ОДИН вход читает код напрямую из
Redis (тот же уровень доверия, что и запуск `docker compose exec` на
этом же деплое, которым уже обладает тот, кто запускает smoke-тест) —
все ПОСЛЕДУЮЩИЕ входы (пассажир, водитель) идут через настоящий
документированный эндпоинт, что заодно доказывает его работоспособность.

## Обходной путь для подбора водителя (pre-existing пробел, не из этой задачи)

`DispatchService.findCandidates()` нигде не вызывается за пределами
собственного unit-теста — в кодовой базе нет ни одного реального
триггера (крон, обработчик события, эндпоинт) для этого движка. Уже
существующий `scripts/simulate-trip.ts` обходит это, записывая
`DispatchAttempt`/`DispatchAttemptLog` напрямую через Prisma —
`staging-smoke.ts` делает то же самое (`seedDispatchMatch`), чтобы
проверить ОСТАЛЬНОЙ жизненный цикл (ставки, выбор, платёж, GPS,
завершение) end-to-end, а не блокироваться на этом отдельном
недостающем куске. Если/когда появится реальный триггер диспетчеризации,
этот обход можно будет убрать.

## Как читать провал

Каждый шаг логирует структурную JSON-строку (`{"event": "...", ...}`) —
последнее событие перед падением обычно указывает, какая именно проверка
не прошла. `AssertionError`-подобное сообщение содержит человекочитаемое
объяснение (например, `Expected trip to be SETTLED, got PAYMENT_FAILED`).

## Полная симуляция с движением по маршруту

`pnpm staging:smoke` — быстрая проверка (одна точка GPS на пикапе, без
реального проезда по маршруту). Для полной симуляции с честным
проездом по геометрии маршрута (как в `apps/admin-web/app/staging` —
раздел «Симулятор поездки») используйте существующий
`scripts/simulate-trip.ts`, указав `API_URL` на staging:

```bash
API_URL=https://<STAGING_API_DOMAIN>/api/v1 pnpm --filter @resilient-taxi/api simulate:trip
```

Он не запускается по кнопке из admin-web: ему нужны `tsx`/Prisma CLI —
инструменты разработки, которых сознательно нет в собранном production-like
образе `api` (см. `docs/staging/security.md`, раздел про Dockerfile).
