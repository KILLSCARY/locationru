# Безопасность staging

## Список «никогда не логировать»

`redactSensitiveData` (`apps/api/src/observability/sensitive-data.ts`)
редактирует по имени ключа (точное совпадение для коротких/неоднозначных
слов — `code`, `otp`, `pin`, чтобы не задеть легитимные `statusCode`/
`errorCode`; совпадение по подстроке для длинных однозначных слов —
`password`, `secret`, `token`, `authorization`, `passport`, `iban`,
`cvv`, `cardnumber`) и маскирует по значению номера телефонов вида
`+7...` в свободном тексте. Никогда не должны попасть в лог: OTP,
access/refresh токены, заголовок Authorization, паспортные данные,
банковские реквизиты, полные номера телефонов, WebSocket auth-токен,
секреты платёжных вебхуков.

### Два бага, найденных и исправленных при реализации

1. **Ключи по regex с границей `_`** изначально не матчили camelCase
   (`accessToken`/`refreshToken`), потому что паттерн требовал границу
   `_` или начало строки перед словом — исправлено переходом на
   комбинацию «точное совпадение для коротких слов + подстрока для
   длинных», которая по построению не зависит от регистра/разделителей.
2. **Маскирование телефонов ломало UUID в `requestId`/`traceId`.**
   Исходный паттерн `\+?\d[\d\s().-]{7,}\d` (необязательный `+`) матчил
   ЛЮБОЙ фрагмент из цифр/дефисов длиной 8+ символов — в том числе
   цифро-дефисные сегменты внутри UUID (например, `1728-4483`), даже
   если рядом были буквы. В реальном прогоне это проявилось как частично
   замаскированный `requestId` в структурном логе (`3052d03d-...` →
   `3052d03*********83-b444-...`), что убивало саму цель
   requestId — корреляцию запросов. Исправление: паттерн теперь требует
   ведущий `+` (`\+\d[\d\s().-]{7,}\d`) — в этой кодовой базе номера
   телефонов всегда нормализованы в E.164 с `+`, а UUID никогда `+` не
   содержит, так что это устраняет ложные срабатывания, сохраняя
   реальное маскирование телефонов в сообщениях об ошибках.

Оба бага покрыты тестами в `sensitive-data.spec.ts`.

## StagingOnlyGuard и модель доступа staging-tools

`apps/api/src/staging-tools/` целиком существует только при
`APP_ENV=staging` (`StagingOnlyGuard` бросает `NotFoundException` — не
`ForbiddenException` — если это не так: снаружи staging этот раздел API
как будто не существует вообще, а не «существует, но недоступен»).
Дополнительно: `@Roles('SUPER_ADMIN')`, `@ApiExcludeController()`
(исключён из Swagger в любом окружении, включая сам staging), каждое
действие пишет запись в `admin_audit_logs`.

## CORS и WebSocket

- CORS включается только при непустом, явном списке разрешённых
  источников без `"*"` (Joi отклоняет `"*"` безусловно, в любом
  окружении). Пустой список = поведение как раньше (permissive-by-omission
  для локальной разработки, где нет браузерных cross-origin клиентов).
- WebSocket-гейтвей (`realtime.gateway.ts`) добавляет: проверку Origin
  при подключении (то же правило «пустой список = не проверяем»);
  лимит одновременных соединений на пользователя
  (`WEBSOCKET_MAX_CONNECTIONS_PER_USER`); вытеснение дублирующей сессии
  при переподключении (старый сокет для того же `sessionId`
  отключается, чтобы не получать события дважды); heartbeat и
  отключение «зависшего» клиента через встроенный механизм Socket.IO
  (`pingInterval`/`pingTimeout`), а не самодельный протокол; rate-limit
  на события (`WEBSOCKET_EVENT_RATE_LIMIT_PER_MINUTE`) — тот же паттерн
  fixed-window через Redis, что и `MapsRateLimitService`, с fail-open
  при недоступности Redis. Межкомнатный доступ (нельзя войти в чужую
  комнату поездки) был уже реализован в `RealtimeAuthorizationService` до
  этой задачи — эта партия работы добавляет вокруг него гигиену
  соединений.

## Production-like Dockerfile: почему в образе `api` нет `tsx`

Финальный образ `api` собирается через `pnpm deploy --prod` (пруненный
вывод только с production-зависимостями) — там сознательно нет `tsx`,
Prisma CLI и каталогов `prisma/`/`test`/`src`-исходников. Это значит:
`scripts/simulate-trip.ts` и `apps/api/scripts/staging-smoke.ts`
(которым нужен `tsx`) не могут быть запущены ИЗ работающего
production-like контейнера `api` — они запускаются через отдельный
one-off контейнер, собранный из `build`-стадии (та же, что использует
сервис `migrate`), у которой есть весь монорепозиторий и dev-зависимости.
Именно поэтому кнопка «запустить симулятор поездки» в admin-web не
реализована как обычная кнопка — см. `docs/staging/smoke-tests.md`.

## Миграции: осторожность с диффом Prisma и PostGIS

Диффовый движок Prisma не моделирует `Unsupported("geography(...)")`
колонки и созданные вручную raw-SQL GIST-индексы на них — это значит,
что ЛЮБАЯ новая миграция рискует получить сгенерированный
`migration.sql` с посторонними `DROP INDEX`/`DROP DEFAULT`
инструкциями, не имеющими отношения к реальному намеченному изменению.
При добавлении роли SUPER_ADMIN и модели `StoredDocument` в этой задаче
сгенерированный файл предлагал (помимо нужных изменений) снести 5
пространственных GIST-индексов и default `gen_random_uuid()` у 8 таблиц
— оба факта проверены напрямую через `psql` как реально существующие и
важные для продакшн-подобной нагрузки (первое — производительность
пространственных запросов, второе — генерация ID). `migration.sql` был
вручную очищен до только нужных инструкций перед применением.
**Правило на будущее**: каждый сгенерированный `migration.sql` в этом
проекте требует ручной проверки перед `prisma migrate deploy` — Prisma
здесь не может быть слепо доверена.
