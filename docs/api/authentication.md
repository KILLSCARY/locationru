# Авторизация

API использует вход по одноразовому SMS-коду и отдельные сессии устройств.

## Endpoints

- `POST /api/v1/auth/request-code` — запросить шестизначный OTP;
- `POST /api/v1/auth/verify-code` — проверить OTP и создать сессию;
- `POST /api/v1/auth/refresh` — выполнить rotation refresh token;
- `POST /api/v1/auth/logout` — отозвать текущую сессию;
- `GET /api/v1/auth/me` — получить текущего пользователя.

`logout` и `me` требуют заголовок `Authorization: Bearer <accessToken>`.

## OTP

Телефон нормализуется в E.164. Российские номера без международного префикса
нормализуются с кодом `+7`. OTP действует ограниченное время и хранится в Redis
только как HMAC-SHA256. Redis также хранит счётчики запросов и неправильных
попыток.

SMS-провайдер выбирается фабрикой `createSmsProvider` по конфигурации
(`SMS_PROVIDER`). Вне production по умолчанию используется
`DevelopmentSmsProvider`: в development код выводится через структурированный
лог, в test — не выводится. В production обязателен `SMS_PROVIDER=http` и
боевой `HttpSmsProvider` (base URL, ключ и sender задаются переменными
`SMS_*`); development-провайдер запрещён на уровне env-валидации и фабрики.
Пока `HttpSmsProvider.sendCode` не подключён к конкретному шлюзу, он кидает
`NotImplemented`, чтобы одноразовые коды не терялись молча.

## Токены и сессии

Access token является короткоживущим JWT и содержит ID пользователя, ID сессии и
массив ролей. Refresh token — непрозрачная случайная строка, привязанная к
`DeviceSession`.

В PostgreSQL хранится только `scrypt`-хеш refresh token. При каждом обновлении
refresh token заменяется. Повторное использование старого token расценивается
как компрометация и отзывает соответствующую сессию устройства.

Каждый logout отзывает только текущую сессию, не затрагивая остальные устройства
пользователя.
