# Roadmap

Дорожная карта развития платформы Resilient Taxi. Документ отражает текущее
состояние кода на ветке разработки и порядок дальнейших работ. Приоритеты
выстроены так, чтобы сначала закрыть «временные ограничения этапа», явно
отмеченные в архитектурной документации, а затем расширять клиентов.

## Условные обозначения

- ✅ — реализовано и покрыто тестами
- 🟡 — реализована архитектура/интерфейс, внешняя интеграция ещё dev-заглушка
- ⬜ — запланировано, не начато

## Текущее состояние

### Backend (`apps/api`, NestJS + Prisma + PostGIS + Redis)

| Домен                               | Статус | Комментарий                                                         |
| ----------------------------------- | :----: | ------------------------------------------------------------------- |
| Auth (OTP, JWT, refresh)            |   🟡   | Логика готова; SMS через `DevelopmentSmsProvider` (код в лог)       |
| Trips + машина состояний            |   ✅   | Централизованный `trip-state-machine`                               |
| Dispatch (подбор водителей)         |   🟡   | PostGIS-поиск готов; ETA по прямой, без routing API                 |
| Driver locations (live + история)   |   ✅   | Валидация скорости, устаревания, rate limit                         |
| Bids (ставки водителей)             |   ✅   | TTL-ставки                                                          |
| Finance (комиссии, payout)          |   ✅   | Снапшот тарифа в транзакции создания поездки                        |
| Payments                            |   🟡   | Интерфейс + вебхуки + идемпотентность; `DevelopmentPaymentProvider` |
| Realtime (WebSocket + outbox)       |   ✅   | Транзакционный outbox, поллинг                                      |
| Admin (аудит)                       |   ✅   | REST под `/api/v1/admin`                                            |
| Health (`/health`, `/health/ready`) |   ✅   | Проверка PostgreSQL и Redis                                         |

## Этап 1. Закрыть внешние интеграции ядра

Цель — заменить `Development*`-провайдеры на реальные и снять пометки
«временное ограничение этапа». Интерфейсы уже спроектированы, работа
локализована за абстракциями.

### 1.1 Платёжный провайдер 🟡

Каркас готов: выбор провайдера по окружению и боевая заготовка на месте.
Осталось подключить конкретный шлюз.

- [x] Провайдер выбирается фабрикой (`payment-provider.factory.ts`):
      `development` вне production, `http` — в production.
- [x] Секреты провайдера через env + Joi-валидация (`PAYMENTS_*`); в
      production `PAYMENTS_PROVIDER=http` обязателен.
- [x] Боевая заготовка `HttpPaymentProvider` с HTTP-клиентом (base URL,
      авторизация, таймаут) и реальной проверкой HMAC-подписи вебхуков;
      денежные методы кидают `NotImplemented`, чтобы прод не имитировал
      платежи.
- [x] Идентификатор провайдера (`provider.name`) пишется в intent/payout/
      webhook вместо хардкода `'development'`.
- [ ] Реализовать методы `HttpPaymentProvider` под конкретный шлюз (ЮKassa /
      T-Bank / CloudPayments) через хелпер `request()`.
- [ ] Полный цикл: авторизация → списание → возврат; маппинг статусов на
      домен поездки.
- [ ] E2E-тесты сценариев успех/отказ/возврат/повторный вебхук на реальном
      (sandbox) шлюзе.

### 1.2 SMS-провайдер 🟡

Каркас готов по образцу платежей. Осталось подключить конкретный шлюз.

- [x] Провайдер выбирается фабрикой (`sms-provider.factory.ts`):
      `development` вне production, `http` — в production.
- [x] Конфигурация через env + Joi-валидация (`SMS_*`); в production
      `SMS_PROVIDER=http` обязателен.
- [x] Боевая заготовка `HttpSmsProvider` с HTTP-клиентом (base URL,
      авторизация, sender, таймаут); `sendCode` кидает `NotImplemented`,
      чтобы прод не «терял» OTP молча.
- [x] `DevelopmentSmsProvider` логирует OTP только при
      `NODE_ENV=development`.
- [ ] Реализовать `HttpSmsProvider.sendCode` под конкретный шлюз через
      хелпер `request()`.
- [ ] Ретраи и обработка ошибок доставки, метрики отправки.

### 1.3 Диспетчеризация: реальный routing 🟡

Seam маршрутизации готов: геопоиск-предфильтр в SQL + уточнение ETA поверх
шортлиста. Осталось подключить конкретный routing API.

- [x] Введён интерфейс `RouteEstimator` (`dispatch/routing/`) и фабрика
      выбора по `DISPATCH_ROUTING_PROVIDER`.
- [x] `StraightLineRouteEstimator` (по умолчанию) сохраняет текущее
      поведение; координаты кандидатов и pickup возвращаются из SQL для
      будущего routing.
- [x] `HttpRouteEstimator` — боевая заготовка с HTTP-клиентом и **фолбэком
      на прямую** при недоступности API (не ломает диспетчеризацию).
- [x] После уточнения ETA кандидаты пересортировываются.
- [ ] Реализовать `HttpRouteEstimator.fetchDurations` под конкретный routing
      API (учёт дорог и пробок) через хелпер `request()`.
- [ ] Кэширование результатов маршрутизации.

## Этап 2. Приложение водителя (`driver-android`)

Приложение реализовано полнее, чем «заготовка»: основной флоу собран в `:app`
(`MainActivity` + `DriverWorkspaceViewModel`), локационная подсистема
проработана. Экраны в `feature/*` — пока неиспользуемые заглушки.

Уже готово в коде:

- [x] Auth-флоу (телефон → OTP), хранение токенов и восстановление сессии
      (`TokenStorage`, `DriverWorkspaceViewModel`).
- [x] Список заказов и ставки (принять цену / своя цена / отозвать),
      сохранение активной ставки.
- [x] Отправка геолокации (батч + офлайн-очередь) и foreground-сервис в
      `core/location`.
- [x] Realtime через socket.io.
- [x] Доменная логика вынесена в чистый JVM-модуль `domain` и покрыта
      unit-тестами: нормализация телефона (совпадает с серверным
      `PhoneNormalizer`), валидация OTP, расчёт комиссии/дохода (совпадает с
      серверным `FareCalculator`).

Осталось:

- [ ] Подключить экраны `feature/*` к навигации или удалить неиспользуемые
      заглушки.
- [ ] Экран активной поездки и её жизненный цикл (`feature/active-trip`).
- [ ] Экраны home / earnings.
- [ ] Согласовать ставку комиссии клиента (сейчас оценочные 15%) с серверной
      настройкой (`FINANCE_GLOBAL_COMMISSION_BASIS_POINTS`, по умолчанию 8%).

> Примечание: Android-модули (`:app`, `feature/*`, `core/*`) требуют Android
> SDK и здесь не собираются; проверяется только чистый JVM-модуль `domain`
> (`gradle :domain:test`).
