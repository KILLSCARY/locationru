# Известные пробелы и невыполненные по объёму задачи пункты

Собранный в одном месте список того, что Задача 29 сознательно не делает —
либо потому что спецификация явно это запрещает ("Не добавляй"), либо
потому что это выходит за рамки объёма задачи и отложено. Ничего из этого
не является забытым — каждый пункт также отмечен комментарием в
соответствующем файле кода.

## Явно запрещено спецификацией (раздел "Не добавляй")

- Платёжная система не подключается; `DevelopmentPaymentProvider` не
  менялся вообще.
- Никаких выплат, банковских карт, финансовых реквизитов — нигде в схеме,
  DTO или UI Задачи 29 таких полей нет.
- Автоматическое OCR паспорта — не реализовано; поля вроде номера
  документа (если появятся в форме) заполняются ровно тем, что ввёл
  человек, никакого распознавания с фото.
- Распознавание лиц — не реализовано; `SELFIE_WITH_DOCUMENT` — просто ещё
  один тип документа, который смотрит человек, автоматического сравнения
  с фото из паспорта нет.
- Автоматическое одобрение водителя — невозможно ни при каких условиях:
  единственный путь к `APPROVED` — вызов `VerificationAdminService
.approveDriver` человеком-администратором (см. `verification.md`).
- Публичные документы — ничего из загруженного не публикуется, весь доступ
  идёт через короткоживущие подписанные URL (см.
  `../security/document-storage.md`).
- Финальный дизайн — admin-web/driver-android/passenger-mobile экраны
  функциональны, но не проходили дизайн-ревью.

## Биометрия зарезервирована, но не включена (раздел 23)

`DriverConsentType.BIOMETRIC_PROCESSING_FUTURE` существует в схеме как
зарезервированное значение и явно **исключён** из `ACCEPTABLE_CONSENT_TYPES`
(`RecordConsentDto`) и из `REQUIRED_CONSENT_TYPES` — водитель не может дать
это согласие через API, потому что реальная биометрическая обработка не
реализована. Значение оставлено в enum намеренно — на случай, если
биометрия появится позже, чтобы не пришлось менять схему БД задним числом.

## Регистрация нового водителя — только вне API (не пробел Задачи 29, но важно для эксплуатации)

Любой новый номер телефона при верификации по OTP получает роль
`PASSENGER` (`AuthService.verifyCode`) — самостоятельной точки входа "стать
водителем" в системе нет. Реальные водительские аккаунты создаются вне
HTTP API (так же, как `prisma/seed-staging.ts` создаёт тестового водителя
напрямую через Prisma) — вероятно, через отдельный процесс
партнёрского онбординга, который не входит в эту задачу. Это ограничение
существовало до Задачи 29 и не является чем-то, что эта задача должна была
исправить — только явно задокументировать, потому что
`staging-test-driver-verification.ts` пришлось обойти его напрямую через
Prisma (см. комментарий в файле).

## `CHANGES_REQUESTED` без push-уведомления

Нет отдельного `NotificationType` для "администратор запросил изменения" —
только `DRIVER_ACCOUNT_APPROVED`/`DRIVER_ACCOUNT_REJECTED`. Водитель узнаёт
о `CHANGES_REQUESTED` и комментарии администратора только через `GET
drivers/me/profile` (см. `verification.md`). Добавление типа — изменение
схемы (`NotificationType` enum + шаблон), сознательно вынесено за рамки.

## `moveToVerifiedStorage` реализован, но не вызывается

См. `../security/document-storage.md` — метод перемещения одобренного файла
из `quarantine/` в `verified/` существует на уровне `ObjectStorageProvider`,
но `VerificationAdminService.approveDocument` его не вызывает: одобрение
меняет только статус строки в БД. Оставлено как задел на будущее, а не
забытый вызов.

## Нет bulk-операций для администратора

Каждое решение (approve/reject документа, автомобиля, водителя) — отдельный
HTTP-вызов. Нет "одобрить все документы этого кейса одним вызовом" — при
большой очереди это означает много последовательных кликов в admin-web
(см. `admin-web/app/driver-verification/`). Тот же класс пробела, что и у
push dead-letter retry (`../runbooks/push-provider-outage.md`).

## driver-android: упрощённый, но рабочий флоу загрузки

`OnboardingScreens.kt` (файловый KDoc-комментарий подробно перечисляет
это): нет UI для обрезки кадра после съёмки, путь через камеру использует
уменьшенный превью-кадр (`TakePicturePreview`), а не полное разрешение (
чтобы не заводить `FileProvider`), нет офлайн-очереди с возобновлением
загрузки после перезапуска приложения. Все эти три пункта — реальная,
но сознательно упрощённая реализация, не полная по исходным 11 шагам
спецификации раздела про загрузку.

## Требуемые списки типов документов/согласий не выдаются публичным эндпоинтом

И `driver-android` (`RequiredDocuments` object в
`DriverWorkspaceViewModel.kt`), и `staging-test-driver-verification.ts`
хранят списки обязательных типов документов/согласий как захардкоженные
константы, синхронизированные вручную с `.env.staging.example`/
`configuration.ts`, а не запрошенные динамически — сервер не отдаёт эти
списки ни одним эндпоинтом. Если дефолтные значения переменных окружения
поменяются, клиенты и staging-скрипт придётся обновить вручную.
